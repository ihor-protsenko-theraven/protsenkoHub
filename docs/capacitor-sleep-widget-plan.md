# План мобільного застосунку та віджета сну

## Стан виконання — 25 жовтня 2026

- Етап 0: використано робочі ідентифікатори `com.protsenko.hub` і `group.com.protsenko.hub`. Вебверсія та API доступні на `https://protsenko-hub.vercel.app`; Apple Developer Program поки немає.
- Етап 1: створено Capacitor 8, Android/iOS проєкти, окрему мобільну Angular-збірку без service worker. `build:mobile` та `cap sync` проходять із реальною HTTPS-адресою; Android debug APK зібрано. Запуск на пристроях та Xcode-збірку ще не перевірено.
- Етап 2: реалізовано мобільну сесію з Bearer access token, ротацією refresh token, відкликанням і захищеним сховищем. Вебавторизація через cookie збережена. Перевірка на телефонах чекає на розгортання нових маршрутів API.
- Етап 3: компактний `GET /api/v1/children/sleep/widget` і синхронізація з застосунку реалізовані. API-тести проходять.
- Етап 4: Android App Widget та iOS WidgetKit extension додані у вихідний код. Android debug APK із віджетом зібрано; iOS-компіляцію й поведінку на пристроях ще потрібно перевірити.
- Етап 5: додано окремий JWT лише для маршрутів віджета, Android receiver та iOS App Intent для прямої паузи/продовження, перевірку сеансу й ревізії перед дією, обробку конфлікту, відсутності мережі та виходу. Android-код компілюється; production API ще не містить мобільних маршрутів, сценарій на двох телефонах не перевірено.
- Етап 6: нативні push і магазинні релізи ще не виконані.

Браузерний сценарій `/app/sleep` з мокованим API перевірив помилку завантаження, повтор, порожній стан і старт сну. Це не перевірка реальної бази чи телефона. [Візуальний макет віджета](design/sleep-widget-preview.png) показує чотири стани, але не замінює перевірку нативного вигляду.

Команди підготовки, підпису та перевірки: [mobile-setup.md](mobile-setup.md).

## Ціль і поточна основа

Підтримувати три клієнти одного сімейного API: вебверсію/PWA на Vercel, застосунок Android і застосунок iOS. Мобільні застосунки використовують зібраний Angular-інтерфейс через Capacitor. Віджети малюються нативно та показують компактний стан сну: ім'я дитини, стан, тривалість або наступний час і одну відповідну дію.

`apps/web` збирається в `apps/web/dist/web/browser`, PWA використовує Angular service worker, а `vercel.json` спрямовує `/api/*` до NestJS. Вебклієнт запитує відносний `/api/v1` з cookie `access_token` (`HttpOnly`, `SameSite=Lax`); мобільна збірка використовує HTTPS API й окрему Bearer-сесію з ротацією refresh token. Екран сну читає повний огляд з історією, а віджети — компактний snapshot; синхронізація між телефонами відбувається після наступного звернення до API. Нагадування PWA працюють через Web Push.

## Узгоджені передумови

- Mac є, але акаунта Apple Developer Program поки немає; на Mac потрібно перевірити наявність Xcode. Застосунок можна підготувати для локальної iPhone-перевірки. Підпис і перевірку WidgetKit з App Group потрібно підтвердити в Xcode; TestFlight та App Store чекають на акаунт.
- Обидва параметри `MOBILE_API_ORIGIN` і `MOBILE_WEB_ORIGIN` для поточного Vercel-розгортання дорівнюють `https://protsenko-hub.vercel.app`. Під час перевірки нові мобільні маршрути на production повертали 404; перед повноцінним тестом на телефонах потрібно розгорнути поточний API та міграції. Адреси передаємо під час збірки, не фіксуємо у вихідному коді.
- Робочі ідентифікатори застосунку можна змінити до підпису й реєстрації в магазинах.

## Етап 0. Зафіксувати параметри мобільного релізу

- Обрати назву застосунку, Android application ID, iOS bundle ID, мінімальні версії ОС та власників облікових записів розробника. Для прямої кнопки WidgetKit орієнтуватися на iOS 17+; на старіших версіях залишити перехід у застосунок.
- Підготувати реальний Android для першої перевірки та Mac з Xcode й iPhone для iOS. На поточному Windows-середовищі можна розробляти спільний код і Android, але фінальна iOS-збірка потребує macOS/Xcode.
- Визначити канал спочатку для сімейного тесту: підписаний Android APK або внутрішній тест Google Play; iOS TestFlight. Для постійного використання окремо підготувати релізи в магазинах.

**Готово, коли:** ідентифікатори та тестові пристрої визначені, а спосіб тестового встановлення на обох платформах доступний.

## Етап 1. Додати Capacitor без зміни вебрелізу

- Створити окремий мобільний проєкт, наприклад `apps/mobile`, з Capacitor-конфігурацією та нативними проєктами `android` і `ios`; брати web assets із Angular production build.
- Додати відтворювані команди `build:mobile`, `sync:mobile`, запуску Android/iOS і перевірку CI. Зафіксувати сумісні версії Capacitor, Android SDK та Xcode.
- Зробити платформну конфігурацію: у вебзбірці лишити маніфест і Angular service worker, у нативному WebView не реєструвати web service worker. Перевірити маршрути `/login`, `/app/home`, `/app/sleep`, повернення з фону та deep link із віджета.
- Залишити чинну Vercel-збірку вебверсії й API окремою від мобільних збірок.

**Готово, коли:** оболонка запускає зібраний Angular на Android та iPhone, навігація працює, а веб/PWA після змін працює як раніше.

## Етап 2. Налаштувати API та мобільну сесію

- Для мобільної збірки використовувати абсолютну HTTPS-адресу API замість поточного відносного `/api/v1`. Перевірити CORS для origin нативного WebView; не розширювати його до `*`.
- Зберегти cookie-контракт вебверсії. Додати окрему мобільну сесію: короткоживучий Bearer access token, refresh token із ротацією та серверним відкликанням. Поточний `JwtStrategy` уже читає Bearer; потрібні видача, оновлення, зберігання й вихід із сесії.
- Зберігати секрети мобільної сесії в захищеному сховищі на базі iOS Keychain / Android Keystore, а не в `localStorage`. Angular HTTP-клієнт має додавати Bearer лише в нативному режимі. Після logout очищати також знімок віджета.
- Не переносити семиденний веб-JWT у JSON як готове рішення: зараз його не можна відкликати після виходу.

**Готово, коли:** на обох телефонах працюють вхід, повторний запуск, оновлення протермінованої сесії, вихід, перевстановлення та доступ після втрати/повернення мережі; вхід PWA не регресував.

## Етап 3. Виділити серверний стан для віджета

- Додати компактний household-scoped snapshot сну замість передачі віджету повного 21-денного огляду. Поля: ім'я, `serverNow`, часовий пояс, стан `idle | sleeping | paused | stale`, `sessionId`, початок і накопичені паузи або підтверджена тривалість, `nextSleepAt`, час отримання даних.
- Формувати прогноз і стан на сервері з чинної логіки сну; не копіювати її у Swift або Kotlin. Після кожної успішної зміни сну з мобільного застосунку оновлювати snapshot і просити ОС оновити віджет.
- Задати явні стани віджета: немає запису, активний сон, пауза, офлайн/застарілі дані, потрібен вхід. Показувати час останньої успішної синхронізації; локальний таймер не робити підтвердженням актуальності серверного стану.

**Готово, коли:** API-тести покривають усі стани й ізоляцію родин, а зміна сну з вебверсії відображається після наступної синхронізації мобільного застосунку.

## Етап 4. Перший компактний віджет

- Android: App Widget через Glance або `RemoteViews`. iOS: WidgetKit extension зі спільним контейнером App Group. Вибір Android-реалізації зафіксувати після прототипу таймера й перевірки різних launcher-ів.
- Спершу показувати підтверджений snapshot і одну дію, яка відкриває `/app/sleep`. Так віджет корисний без доступу extension до облікових секретів. Завершення сну завжди відкриває екран застосунку для підтвердження.
- Для тривалості використати системний динамічний текст на iOS і `Chronometer` на Android, якщо прототип правильно враховує паузи. Фонове оновлення стану другого з батьків може затримуватися; при застарілих даних показувати це явно.
- Перевірити приватність і читабельність імені дитини на заблокованому екрані та у різних розмірах віджета.

**Готово, коли:** на обох реальних пристроях віджет додається, показує кожен стан, відкриває потрібний екран, коректно реагує на вихід і не видає застарілий стан за поточний.

## Етап 5. Додати пряму дію «Пауза / Продовжити»

- Для кнопки без відкриття застосунку додати нативний обробник: `AppIntent` на iOS та дію віджета на Android. Початок сну лишити переходом у застосунок для вибору денного/нічного сну; завершення — для підтвердження.
- Окремо спроєктувати захищений доступ обробника до API. На iOS застосунок і extension можуть ділитися Keychain-групою, але одночасна ротація одного refresh token потребує узгодження; перевірити модель окремої сесії віджета або централізованого оновлення через застосунок.
- Перед мутацією звіряти актуальний `sessionId` і стан із сервером. API має відхиляти дію зі старої картки, якщо інший із батьків уже завершив цей сон або почав новий. Після відповіді перечитати snapshot; при `401`, конфлікті чи втраті мережі показати помилку без удаваного успіху.

**Готово, коли:** пауза/продовження працюють з віджета на двох платформах; тести охоплюють подвійний тап, стару картку, одночасні дії батьків, протерміновану й відкликану сесію.

## Етап 6. Сповіщення, перевірка та випуск

- Зберегти чинні Web Push нагадування для PWA. Для повноцінного мобільного релізу окремо підключити нативні push-сповіщення через APNs/FCM та перевірити той самий сценарій нагадувань. Нативний екран не повинен обіцяти Web Push, бо в цій збірці service worker вимкнено.
- Виконати `npm run typecheck`, `npm test`, production build веб/API та окремі Android/iOS збірки. У браузері перевірити PWA: порожній стан, помилку й основні дії сну. На пристроях: вхід/вихід, відновлення після перезапуску, офлайн, часовий пояс, заблокований екран, віджет і зміну сну другим із батьків.
- Спершу випустити внутрішні збірки через Google Play internal testing та TestFlight. Після перевірки й налаштування підпису, політик магазину та метаданих випустити production-версії.
- Вести окремі релізи: Vercel оновлює веб/PWA та API; зміни вбудованого Angular-коду або нативного віджета потрапляють на телефони через нову версію мобільного застосунку. API-зміни мають лишатися сумісними зі встановленими версіями.

**Готово, коли:** два батьки можуть використовувати веб, Android та iPhone з одним станом сну, а віджет на обох ОС показує підтверджений стан і виконує узгоджену дію.

## Контрольні точки

1. Після етапу 2 — робочий мобільний застосунок із тим самим акаунтом і даними.
2. Після етапу 4 — перший придатний для сімейного тесту віджет із переходом до сну.
3. Після етапу 5 — інтерактивна пауза/продовження без відкриття застосунку.
4. Після етапу 6 — мобільний реліз із перевіреними сповіщеннями.
